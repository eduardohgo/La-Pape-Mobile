# Riesgo de dependencias: Expo CLI y Zod

Revisión: 27 de octubre de 2026. Alcance: migración Expo SDK 58 de La Pape Mobile, PR #130, e integración de Actividad 4, PR #131.

## Resultado observado

`npm audit --json` reporta tres paquetes con severidad alta y cero críticos. Son tres entradas de una misma cadena transitiva, no tres vulnerabilidades independientes:

| Paquete | Versión instalada | Origen del aviso |
|---|---|---|
| expo | 58.0.20 | Propaga el aviso de @expo/cli |
| @expo/cli | 58.1.16 | Propaga el aviso de zod |
| zod | 3.25.76 | GHSA-mrhx-c7xc-m3w5 |

Fuentes: [GitHub Advisory Database](https://github.com/advisories/GHSA-mrhx-c7xc-m3w5), [corrección upstream](https://github.com/colinhacks/zod/pull/6652). El aviso describe agotamiento de memoria al validar colecciones excesivas y publica 4.6.6 como versión corregida. npm audit devuelve exit 1 mientras persiste: no se trata como auditoría aprobada.

## Exposición comprobada y límites de la revisión

No se encontraron importaciones directas de Zod en frontend/src ni backend/src. La instancia vulnerable está bajo expo/node_modules y pertenece a las herramientas de desarrollo, no a un validador escrito para nuestra API.

En @expo/cli/build/src/start/server/DevToolsPlugin.schema.js existen colecciones para metadatos y salida de plugins. DevToolsPluginCliExtensionResults.parseOutputText valida JSON producido por plugins con DevToolsPluginOutputSchema.safeParse; createMCPDevToolsExtensionSchema construye esquemas para comandos de extensiones. Por tanto, hay entradas de plugins/extensiones en el proceso Node de desarrollo que justifican conservar el aviso. Que no exista importación directa en la aplicación no elimina el riesgo de la CLI.

No se demostró un camino remoto explotable específico de La Pape ni se ejecutó una prueba de agotamiento de memoria. No se acredita ausencia de exposición en todos los caminos de Expo, ni un análisis completo del bundle de producción. El límite de acumulación de salida que incluye la CLI no equivale a la corrección publicada por Zod. No se descarta el aviso como falso positivo.

## Decisión técnica y riesgo residual

El propietario ha indicado conservar SDK 58 y la arquitectura de Actividad 4, documentar el riesgo y preparar ambos PR, sin forzar Zod 4 ni regresar a Expo antiguo. Esto no significa que la vulnerabilidad esté corregida ni autoriza por sí solo los merges.

La CLI más reciente consultada continúa en 58.1.16 y declara zod ^3.25.76; la última versión 3.x consultada es 3.25.76. No se ha verificado una actualización corregida compatible con ese rango. El fixAvailable de npm propone bajar Expo a 54.0.38: se rechaza porque rompe el objetivo SDK 58. Tampoco se usan overrides de versión mayor, parches manuales de node_modules, --force, --legacy-peer-deps, exclusiones del aviso ni npm audit fix automático.

El riesgo alto permanece abierto y requiere aceptación explícita al autorizar la integración o una corrección upstream compatible. Responsable de decidir: propietario/mantenedor del proyecto. Revisar nuevamente antes del merge, antes de cualquier entrega externa y cuando cambien Expo CLI, Zod o el advisory. No se declara el proyecto libre de vulnerabilidades.

## Medidas operativas de mitigación

Estas son instrucciones de operación; este documento no afirma haber cambiado firewalls, puertos o configuraciones privadas:

- Usar Metro/DevTools solo durante desarrollo y en una red privada de confianza. No publicar sus puertos en Internet ni habilitar túneles públicos para esta revisión. El iPhone con Expo Go necesita una red local accesible; no sustituir esa conexión por localhost en el teléfono.
- Ejecutar únicamente plugins y extensiones de procedencia revisada; no procesar resultados JSON o metadatos de plugins no confiables. No habilitar nuevas extensiones MCP/DevTools como parte de esta integración.
- Mantener CI sin servidores de desarrollo persistentes y sin secretos innecesarios. Las pruebas de catálogo usan transportes simulados; la integración de salud usa un puerto local efímero sin base de datos.
- Instalar con npm ci y los lockfiles revisados. Volver a consultar npm audit y evaluar una corrección compatible tan pronto esté disponible.
- Si se observa consumo anómalo de memoria de la CLI, detener esa sesión de desarrollo, conservar evidencia sin secretos y revisar plugins/entradas. No ejecutar payloads de denegación de servicio en el equipo de trabajo.

Semgrep es SAST con seis reglas locales: que apruebe no corrige este aviso ni sustituye el análisis de dependencias. Las protecciones actuales de develop/main exigen PR y bloquean borrados/force-push, pero no hacen obligatorios los checks CI/SAST; revisar ambos resultados manualmente antes de autorizar cada merge, sin cambiar dichas reglas.

## Reproducción de la revisión

Desde frontend/, sin modificar dependencias:

```powershell
npm audit --json
npm explain zod
npm view @expo/cli@latest version dependencies.zod --json
npm view zod@3 version --json
npx --no-install expo install --check
npx --yes expo-doctor@latest
```

Comprobar por separado exit codes, versiones y cambios del advisory. No interpretar un fallo de red como resultado limpio. Ningún comando anterior crea usuarios, escribe en Neon o autoriza publicar credenciales.

## Condiciones para integrar

1. #130: comprobar CI y SAST del último commit, TypeScript, ESLint, pruebas, matriz SDK y Expo Doctor; el mantenedor decide el tratamiento del riesgo residual documentado.
2. #131: incorporar los commits de #130 en su rama y resolver únicamente el import conflictivo del catálogo, preservando el ViewModel, ComponentRef, casos de uso, Repository y pruebas. No fusionar develop durante esta preparación.
3. Repetir las verificaciones sobre la revisión combinada y revisar en iPhone Splash, navegación, Inicio, Catálogo, filtros/reintento, detalle por UUID e imágenes nulas. Registrar la validación física únicamente cuando se realice.
4. Al autorizar los merges, integrar primero #130 y después #131. Preferir merge commit para conservar la relación de ancestros preparada; si se elige squash/rebase o develop cambia, recalcular el diff de #131 y repetir checks antes de integrarlo. Nunca aprobar automáticamente una nueva revisión por los resultados de un SHA anterior.
